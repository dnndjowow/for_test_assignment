# Карточки приборов

Локальный сервис для подготовки черновиков карточек контрольно-измерительных приборов. Принимает сведения о товаре, обращается к одной модели через OpenRouter и возвращает текст, характеристики и поисковые запросы.

## Запуск

Нужен Python 3.11 или новее. Проект проверен на Python 3.12.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
```

В Windows окружение активируется командой `.venv\Scripts\activate`.

В `.env` укажи ключ OpenRouter:

```dotenv
OPENROUTER_API_KEY=your_key
OPENROUTER_MODEL=openai/gpt-4.1-mini
OPENROUTER_TIMEOUT=45
```

Модель должна поддерживать `response_format: json_schema` и `temperature`. Запрос отправляется с `provider.require_parameters=true`, чтобы выбранный провайдер учитывал эти параметры. Другие модели можно указать в `OPENROUTER_MODEL`; совместимость нужно проверить на их странице в OpenRouter. Ключ хранится на сервере, `.env` исключён из Git.

Для `nvidia/nemotron-3.5-super-vl:free` добавь в `.env`:

```dotenv
OPENROUTER_MODEL=nvidia/nemotron-3.5-super-vl:free
OPENROUTER_REASONING=false
```

Эта модель по умолчанию использует рассуждения, которые тоже занимают лимит ответа. В данном сценарии они отключаются, чтобы лимит использовался для карточки. `OPENROUTER_REASONING` можно оставить пустым для моделей без этой возможности. После изменения `.env` перезапусти приложение.

Запусти приложение из корня проекта:

```bash
uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Открой [интерфейс](http://127.0.0.1:8000) или [описание API](http://127.0.0.1:8000/docs). Страница, примеры и экспорт работают без ключа. Для новой генерации ключ обязателен.

## Использование

1. Выбери демонстрационный товар, вставь JSON или загрузи `.json`.
2. Нажми «Подготовить карточку».
3. Проверь замечания и отсутствующие поля.
4. Скопируй Markdown или скачай JSON.

Кнопка «Посмотреть сохранённый образец» показывает вручную подготовленный эталон. Образцы доступны для знакомства с интерфейсом и проверки формата. Новая генерация всегда обращается к API; автоматической подстановки образца при ошибке нет.

Можно работать из командной строки:

```bash
python generate.py examples/manometer.json
python generate.py examples/thermometer.json --format markdown --output user_data/thermometer.md
```

Коды завершения: `0` — карточка подготовлена, `1` — нужны исходные данные или уточнение, `2` — ошибка входа, конфигурации или генерации. При коде `1` CLI возвращает JSON с замечаниями, в том числе при `--format markdown`.

## Входные данные

```json
{
  "name": "Манометр МД-100",
  "manufacturer": "ДемоПрибор",
  "specs": {
    "Диапазон измерений": "0–1,6 МПа",
    "Класс точности": "1,5",
    "Присоединение": "G1/2",
    "Интерфейс передачи данных": null
  },
  "description": "Прибор предназначен для местного визуального контроля избыточного давления воды и воздуха."
}
```

`name` обязателен. Для генерации также нужна хотя бы одна заполненная характеристика или описание. Значения `specs` передаются строками с исходными единицами, неизвестные — как `null` или пустая строка. Пустые необязательные поля нормализуются в `null`. Неизвестные поля входного JSON отклоняются, чтобы опечатка не осталась незамеченной.

Лимиты: название и производитель — по 180 символов; описание — до 12 000; до 40 характеристик, название каждой — до 120, значение — до 500 символов. POST-запрос ограничен 64 КБ.

## Результат

Карточка содержит SEO-заголовок до 70 символов, SEO-описание на 800–1200 символов, характеристики, 3–5 поисковых запросов и коммерческий блок до 700 символов. Длина считается с пробелами, без внешних пробелов поля.

Дополнительно возвращаются `missing_fields`, `warnings` и счётчики `checks`.

| Статус | Значение |
| --- | --- |
| `ready` | Карточка прошла автоматические проверки, известных пропусков нет |
| `needs_review` | Карточка подготовлена, но некоторые исходные поля отсутствуют |
| `insufficient_data` | Для генерации не хватает сведений; API не вызывается |
| `needs_clarification` | Обнаружено противоречие; текст карточки не возвращается |

Все карточки остаются черновиками. Статус `ready` означает прохождение реализованных проверок формата и значений.

## API

| Метод | Путь | Назначение |
| --- | --- | --- |
| `POST` | `/api/cards` | Подготовить карточку по данным товара |
| `GET` | `/api/examples/manometer` | Данные демонстрационного манометра |
| `GET` | `/api/examples/thermometer` | Данные демонстрационного термометра |
| `GET` | `/api/examples/{id}/result` | Сохранённый эталон результата |
| `POST` | `/api/export/markdown` | Экспорт карточки и замечаний в Markdown |
| `POST` | `/api/export/json` | Экспорт карточки и замечаний в JSON |
| `GET` | `/health` | Проверка запуска приложения |

```bash
curl http://127.0.0.1:8000/api/cards \
  -H 'Content-Type: application/json' \
  --data-binary @examples/manometer.json
```

Некорректный JSON возвращает `400`, неправильные поля — `422`, превышение размера — `413`. Ошибки генерации возвращают понятный `detail` и стабильный `code`. Отдельно обрабатываются отсутствие ключа, отказ в доступе, недостаток средств, лимит запросов, таймаут, пустой и оборванный ответы.

## Промпт и проверки

Системный промпт находится в `app/services/prompts.py`. В нём заданы формат, длина полей и правила: использовать только входные факты, сохранять значения и единицы, явно сообщать о противоречиях. JSON товара передаётся отдельным пользовательским сообщением и рассматривается как данные.

Ответ модели запрашивается по JSON-схеме из `CardDraft`, затем повторно проверяется Pydantic. Таблица характеристик собирается кодом из `specs`, поэтому модель не переписывает её значения. Для `null` выводится «данных нет».

Проверка текста ищет новые числа, сочетания чисел с единицами, технические обозначения и некоторые неподтверждённые обещания: сертификаты, поверку, гарантию и другие. Числа с десятичной запятой и точкой сравниваются одинаково. Простые числовые противоречия вида «название поля: значение» обнаруживаются до запроса. Для конфликта, найденного моделью, проверяются имя исходного поля и наличие точной цитаты в описании.

Если формат или текст не проходит проверку, модели один раз отправляются исходный ответ и конкретные ошибки. После повторной неудачи возвращается ошибка без карточки. Недостающие факты не дополняются ради достижения 800 символов.

Для временной сетевой ошибки или HTTP 408/429/5xx предусмотрен один повтор. Максимум — две генерации, каждая до двух HTTP-попыток. Общий срок подготовки ограничен 120 секундами. Повторные запросы могут увеличивать расход средств.

## Примеры

В `examples/` находятся два **условных товара с вымышленным производителем**. Это демонстрационные данные, подготовленные вместо отсутствующих в задании двух полных наборов. Они не являются характеристиками реальных приборов.

- `manometer.json` — заполненные сведения о манометре.
- `thermometer.json` — термометр с отсутствующими сведениями о датчике, интерфейсе и защите корпуса.
- `results/` — вручную подготовленные эталоны в JSON и Markdown. Они используются и для проверок приложения.
- `generated/` — реальные результаты OpenRouter для обоих демонстрационных товаров; параметры и показатели проверки находятся в `check.json`.

Реальная генерация проверена 7 ноября 2026 года на `nvidia/nemotron-3.5-super-vl:free` с `OPENROUTER_REASONING=false`. Обе карточки прошли автоматические проверки после одной попытки исправления длины. Манометр получил статус `ready`, термометр — `needs_review` с тремя отсутствующими характеристиками. Ответы API сообщили `reasoning_tokens: 0` и стоимость `0` для этого прогона. Доступность бесплатного endpoint и его лимиты могут меняться.

## Тесты

```bash
python -m pip install -r requirements-dev.txt
python -m pytest
```

Тесты используют подменённые ответы и HTTPX MockTransport. Ключ и сетевое подключение им не нужны. Проверяются успешная генерация, пропуски, некорректный вход, противоречия, неподтверждённые значения, исправление ответа, экспорт, CLI, ошибки и ограниченные повторы API.

### Реальная генерация через OpenRouter

Оба демонстрационных товара обработаны моделью `nvidia/nemotron-3.5-super-vl:free` с `OPENROUTER_REASONING=false`:

| Товар | Заголовок, до 70 символов | Описание, 800–1200 символов | Поисковые запросы, 3–5 | Статус |
| --- | --- | --- | --- | --- |
| Манометр МД-100 | 52 | 862 | 4 | `ready` |
| Термометр ТД-200 | 42 | 872 | 3 | `needs_review` |

Первые ответы содержали описания на 755 и 570 символов. Программа выявила нарушение длины и отправила модели замечания. В обоих случаях одного запроса на исправление хватило для прохождения автоматических проверок. Значения в таблицах характеристик совпали с исходными `specs`.

Статус `needs_review` у термометра ожидаем: не заданы тип подключаемого датчика, интерфейс передачи данных и степень защиты корпуса. Эти три поля перечислены в `missing_fields`, а в карточке отмечены как «данных нет».

- [Карточка термометра](examples/generated/thermometer.md) и [JSON-ответ](examples/generated/thermometer.json).

Локальные тесты проверяют предусмотренные сценарии на подготовленных ответах. Реальный прогон подтверждает работу выбранной модели на двух примерах. Смысловую точность формулировок перед публикацией нужно сверять с исходным паспортом.

## Структура

```text
app/
  config.py              настройки и загрузка .env
  main.py                приложение и обработка ошибок
  middleware.py          ограничение размера запроса
  schemas/product.py     входные и выходные схемы
  routers/cards.py       маршруты API
  services/
    llm.py               запросы к OpenRouter
    prompts.py           промпт и JSON-схема ответа
    generation.py        подготовка карточки и исправление ответа
    checks.py            проверки значений и пропусков
    export.py            экспорт Markdown
  static/                интерфейс без сборки и внешних ресурсов
examples/                демонстрационные данные и эталоны
tests/                   автоматические проверки
generate.py              запуск из командной строки
```

## Ограничения и дальнейшие улучшения

- Проверка чисел и обозначений не доказывает смысловую достоверность всего текста. Например, неверное утверждение о сфере применения может не содержать чисел. Перед публикацией нужен просмотр менеджером по исходному паспорту.
- Наличие цитаты подтверждает её происхождение, но не гарантирует правильность вывода о противоречии. Сложные противоречия и таблицы с несколькими модификациями требуют дополнительной обработки.
- Список пропусков строится из основных полей и переданных пустых характеристик. Универсального каталога обязательных параметров для всех типов приборов нет.
- Структурированные характеристики берутся из `specs`. Сведения из `description` могут использоваться в тексте, но автоматически не добавляются в таблицу.
- Поисковые фразы предлагаются моделью; частотность и конкурентность не проверяются.
- Прототип рассчитан на локальный запуск. При развитии сервиса потребуются аутентификация, ограничения расходов и запросов, шаблоны характеристик по типам приборов и набор реальных примеров для оценки качества.
